# Slide outline

Ten slides, one message each, with speaker notes. Draft for review. Keep the deck short: the one-pager
and brief carry the detail.

1. **Title: Keeping SDK docs current**
   Message: a proof of concept that helps keep guides and examples in step with the SDK.
   Notes: introduce yourself and the partner teams involved.

2. **The problem**
   Message: reference pages generate themselves, but guides and examples fall behind.
   Notes: one concrete story of a guide that went stale after an SDK change.

3. **The idea**
   Message: watch the SDK, notice what changed, draft the affected pages, and keep people in charge.
   Notes: use the "careful assistant with a checklist" picture.

4. **How it works (diagram)**
   Message: change in, report out, human review before publishing.
   Notes: use the flow diagram from the brief. Walk it left to right.

5. **Examples are real code**
   Message: each example is a separate script, checked automatically, kept apart from the page.
   Notes: show one page next to its example file. This is the clearest differentiator.

6. **Quality you can explain**
   Message: automatic checks, a reviewer, limited passes, and a report per page.
   Notes: show one report. Point out the "not evaluated" section.

7. **What we found**
   Message: the reviewer caught real gaps, and the system exposed errors in the SDK's own docs.
   Notes: use the key-value store example. Be clear that a passing score is not proof.

8. **How it fits with other work**
   Message: reference to GitHub Pages, guides to dev.splunk.com, and a shared export convention with SplunkUI.
   Notes: show the reuse table. Say what we adopt and what we build, and why.

9. **Where we are**
   Message: proven pieces, open pieces, and honest limits.
   Notes: use the proven versus not-yet table. Do not oversell.

10. **What we need**
    Message: a running Splunk for testing, an approved model route, and sample page sources.
    Notes: end with the next three steps and who owns each.
